## The product question

How do you evaluate an AI agent when success depends on several systems, incomplete information, and actions that change a case? A convincing final answer says little about whether the workflow followed the right rules or handled a failed dependency correctly.

AI Evaluation & Governance Lab is my independent exploration of that problem, with prior authorization as the first planned use case. The current build establishes the environment in which an agent could eventually work: persistent synthetic cases, separate service APIs, and explicit manual actions. Agent execution and evaluation are future milestones.

## The experience

The case workspace brings a fictional patient, supporting documents, and available simulator actions into one view. A person can inspect a referral, request an authored eligibility result, or record a synthetic message. The message receipt confirms storage without implying delivery, and the eligibility result does not change the case status.

Six baseline cases cover differences such as missing documents, ineligible fixtures, and unknown eligibility. The interface distinguishes an empty result from an unavailable service, so a failed request cannot quietly become a reassuring answer. Stored cases and messages survive service restarts.

The services share one local PostgreSQL instance, but runtime code accesses only its own schema. The orchestrator cannot bypass a simulator by reading its tables. Generated OpenAPI contracts connect the Python services to the TypeScript interface.

## Decisions and design lessons

**Build the environment before judging the agent.** Stable fixtures and explicit service contracts make it possible to distinguish a reasoning problem from a broken tool or inconsistent starting state.

**Unknown and unavailable mean different things.** An authored unknown result, a missing record, and a failed service call should remain distinguishable. Collapsing them hides the evidence a reviewer needs.

**A retry needs an identity.** A timeout can occur after a message has been stored. Reusing the same request ID returns the original receipt; different content with that ID is rejected. This makes recovery deliberate before autonomous actions are introduced.

## Current state and next step

The local build supports persistent cases, document inspection, manual eligibility checks, and recorded synthetic messages. The repository documents unit, integration, and browser checks. Runs, Evaluations, and Governance are still placeholders, and no live demo is deployed.

The next milestone is controlled agent execution with tool-call records and durable human review. Independent evaluation and comparisons can then assess what happened across the workflow, using the same synthetic starting conditions. The [repository and roadmap](https://github.com/ktakeuchi21/ai-evaluation-governance-lab) document those boundaries.
